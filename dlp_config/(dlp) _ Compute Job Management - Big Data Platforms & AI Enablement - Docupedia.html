Usage • Computing and Job Scheduling •  Compute Job Management

1. Introduction

In order to utilize the resources of a GPU Cluster as effectively as possible, an efficient management system is required. On the GPU Clusters in Schwieberdingen and Abstatt, this task is handeled by IBM's Platform Load Sharing Facility - or short LSF.
LSF is a workload management and compute job scheduling system, which can be used to execute batch jobs on distributed, networked computing resources. As described in the (dlp) | Overview section, compute nodes form the main part of the GPU cluster. The access to these compute resources is controlled by the job scheduler. A job is for example a software run without interactive processes. If you want to start a job, you have to tell the scheduler the execution command and the accordant resource needs.

1.1. Resource Requirements

Basic requirements are related to questions like

  • How many CPUs?
  • How much memory?
  • How many GPUs?
  • How much time will the job need?

Further details consider

  • Is the parallel job based on shared or distributed memory techniques?
  • Are there any dependencies to results of other jobs?
  • ...

Based on these specifications the scheduler reserves the requested resources if they are available and starts the job. If the requested resources are not available, the job is send to a job queue and will start later.

The basic requirements must cover the maximum need of a job, otherwise the job cancels due to a lack of resources. But while the requested number of GPUs and CPUs usually meets the actual requirements, the difference between request and need of memory and/or runtime often varies widely. Keep in mind, excessive resource requirements have consequences:

  • Big parts of the GPU cluster are allocated but not used due to overdone memory requests.
  • Due to exaggerated runtime requests the scheduling of bigger jobs is hampered.
  • Jobs are pending as resource requirements cannot be satisfied caused by the own request (not need) or caused by the allocated but not used resources of other jobs.

Thoughtful specified resource requests improve the utilization of the GPU system and will make your jobs start earlier!

Please use only one compute node except you know what you are doing and made your software capable of multi-node execution, e.g. with MPI.

1.2. Job Priority

Each waiting job will be assigned a priority that helps the scheduler to determine the best slots for each job. Jobs of users using none or only few compute resources at the moment get a higher priority than jobs of users who already run resource consuming jobs (Fairshare). Own jobs the user can prioritize on submit using option -p. But this value changes only the order of own jobs.

Please note: Smaller jobs may pass larger jobs if these have to wait for resources. The scheduler is using advanced technology to optimally place jobs and minimize waiting times. Nevertheless it is possible for jobs to virtually never run because of their resource requests. Jobs that are submitted but in an "hold" state, e.g. due to user inputs (waiting for other jobs to finish, do have a starting time in the future, set on hold by a user or administrator) will not be considered by the scheduler and do therefore not receive a priority.

If you want to learn more about priorities and the LSF scheduling policies, you can have a look into the IBM LSF Knowledge Center here, here and here.

2. Submission of Compute Jobs

In order to submit a compute job to LSF, the job and the planned resource requirements have to be specified in a job file or batch job script:

IBM LSF requests use the marker #BSUB, so you want to make sure you have these in your submit scripts.

For now, please only use one node for your jobs (#BSUB -R "span[hosts=1]")

Please note that the description of the parameter -M has changed. The amount of memory now refers to memory per CPU core, NOT to memory per host. This might require some calculations.

LSF New GPU Syntax
## Scheduler parameters ## #BSUB -J tensorflow-3.5 # job name #BSUB -o tensorflow-3.5.%J.stdout # optional: have output written to specific file #BSUB -e tensorflow-3.5.%J.stderr # optional: have errors written to specific file #BSUB -q <queue> # optional: select the queue, you would like to use. E.g., batch_a100, batch_h100 #BSUB -W 2:00 # fill in desired wallclock time [hours,]minutes (hours are optional) #BSUB -n 1 # min CPU cores,max CPU cores (max cores is optional) #BSUB -M 2048 # fill in required amount of memory per CPU core(in Mbyte) # #BSUB -R "span[hosts=1]" # optional: run on single host (if using more than 1 CPU core) # #BSUB -R "span[ptile=28]" # optional: fill in to specify cores per node (max 28-40 depending on node type) # #BSUB -P myProject # optional: fill in cluster project #BSUB -gpu "num=1" # Here comes your code # [...]

2.1. Submit Script Templates


You most likely want to submit a job script to the system. These bash scripts contain your job as well as required and optional scheduler commands necessary to schedule the job to a suitable node. The GPU syntax is configured differently across the 3 clusters. Please use the corresponding job scripts based on the defined GPU Syntax.

Batch job script examples for Tensorflow, Theano and PyTorch via the Anaconda virtual environments can be found under:

LSF Job Samples - New GPU Syntax
/fs/applications/lsf/samples/pytorch_new.bsub /fs/applications/lsf/samples/theano_new.bsub /fs/applications/lsf/samples/tensorflow_v1_new.bsub /fs/applications/lsf/samples/tensorflow_v2_new.bsub


Note: The default Tensorflow installation from Conda repository is Tensorflow 2. There are some API changes from Tensorflow 1 (https://www.tensorflow.org/guide/migrate). We would recommend you to use the corresponding job script containing the name *tensorflow_v2*.bsub.

A batch job script can be submitted to the job scheduler using the LSF bsub command:

bsub < your-batch-job-script.bsub

2.2. Limit to number of concurrent GPUs across all running jobs

  • Only applicable for Deep Learning Platform at Renningen (rng-dl01)
  • This does not affect group bookings as the restriction is only at user level.  

There is currently a limit set at 20 concurrent GPUs (V100 & A100) per user for all running jobs at any given time. 

Should you wish to check the number of GPUs being used across all your running jobs, you can use the command:

LSF New GPU Syntax
blimits -u <user-id>
2.2.1.1.1.1. How does the limit  work when I am working with MIG Slices? 

As long as all your MIG slices (MIG =1 or 2 or 7)  are on the same GPU device for your running job, your GPU used count would be 1.  For example: bsub -gpu "num=1:mig=7" or bsub -gpu "num=1:mig=2" , would mean you all your MIG slices are using 1 physical GPU device as represented by parameter (num).

If the num parameter is increased, which means increase in number of physical GPU devices, then your limit also gets updated.

2.3. Interactive Jobs

Interactive jobs can be submitted with or without X forwarding. Please make sure to use the queue "interactive".

With  X forwarding:

LSF New GPU Syntax
bsub -XF -Is -J <job name> -n <number of CPU cores> -W <runtime in hours:minutes> -gpu "num=1:mode=exclusive_process:mps=no" /bin/bash

Without X forwarding:

LSF New GPU Syntax
bsub -Is -J <job name> -n <number of CPU cores> -W <runtime in hours:minutes> -gpu "num=1:mode=exclusive_process:mps=no" /bin/bash

Once your scheduled job is running, you’ll get a prompt on one of the cluster nodes. You can run nvidia-smi to verify the number of available GPUs on the node.

LSF is configured to utilize GPUs in exclusive mode and is using Linux cgroups to attach/map GPU devices and CPU cores to jobs. You will therefore only the the number of GPUs you requested inside your job.

The variable CUDA_VISIBLE_DEVICES is utilized to communicate the requested number of GPUs to the jobs.

If you want to exclude certain hosts from scheduling, e.g. because your task has special memory requirements, you can use the -R option.
Example: The following bsub command submits a job 'mytask' to the rb_highend queue and excludes the hosts rng-dl01-w038 and rng-dl01-w067.

bsub -q batch_v100 -R "select[hname!='rng-dl01-w038' && hname!='rng-dl01-w67']" mytask

2.4. Nvidia  MIG Mode for A100/H100 GPUs

With the latest generation Nvidia A100/H100 GPU the so called Multi Instance GPU mode (MIG mode) has been introduced. With this new operation mode for GPUs it is possible to split one A100/H100 GPU in up to 7 GPU slices. MIG mode can be used with LSF using the following commands and parameters:

For an interactive session with one MIG slice:

LSF Nvidia MIG Mode Syntax
bsub -Is -q inter_a100 -n 4 -M 5120 -W 1:00 -gpu "num=1:mig=1" /bin/bash
LSF Nvidia MIG Mode Syntax
bsub -Is -q inter_a100 -n 4 -M 5120 -W 1:00 -gpu "num=1:mig=1" /bin/bash

For compute jobs/jobfiles:

LSF Nvidia MIG Mode Syntax
Replace -gpu "num=1" with -gpu "num=1:mig=1" (Optional: -gpu "num=1:mig=1/1")

this example gives you a single MIG GPU slice with 10GB of GPU memory.

More information can be found in the IBM LSF documentation.


The nvidia-smi command can be used to gather information on the GPU/MIG instance

4. Schedule Jobs on Highend GPUs (Tesla V100)

To run your job on highend GPUs you must specify this at submission time. You can do so by adding

Abstatt and Braga:

#BSUB -q rb_highend

Renningen:

#BSUB -q batch_a100

to your job script.

Using highend nodes

Please be economical in your use of the high end queue, as otherwise we might be forced to restrict usage to certain use cases.

Good sanity checks for using Tesla A100 GPUs:

Does your workload require or benefit disproportionally from

  • the higher compute power per GPU?
  • the higher memory per GPU (80 GB vs 32 GB)?

Does your workload make use of

  • mixed precision and/or A100 tensor cores?
  • NVlink/NVswitch GPU-to-GPU communication?

Does your workload require scaling out to more than a single node?

  • In that case, please reach out to us

5. Control & Monitoring of Compute Jobs

After successful submission, the user has different options to controling and monitoring compute jobs.

5.1. bjobs

The bjobs command shows the status of submitted jobs, for example whether they are waiting, running or recently finished.

  • -w prevents long lines/content from being clipped
  • -u all shows jobs of all users
  • -l <jobID> shows detailed information about a particular job
  • -r shows all running jobs
  • -p shows all pending jobs
  • -s shows all suspended jobs
  • -m <host> shows all jobs running on a host

Pending jobs are displayed in the order in which they are considered for dispatch. Jobs with higher priority are displayed before those with lower priority. Pending jobs with the same priority are displayed in the order in which they were submitted. This order can be changed by using the commands btop/bbot.

5.2. btop / bbot <jobID>

Increases/decreases the priority of own waiting jobs to change the order in which they are considered for dispatch.

If a normal user executes the command, it will affect only the order of their own jobs.
A user group admin can change the order of all jobs within their group, e.g. prioritizing an important job of a particular user.
LSF administrators can send jobs to the top or bottom of the cluster-wide queue, circumventing any prioritity mechanism. Note that we'd only make use of this in exceptional cases.

Determine reasons for pending jobs

If you are wondering why your job is still pending, you can find a small manual on how to determine why jobs are still pending here.

5.3. bhosts / lsload

Displays a list of all hosts including the following information:

HOST_NAME; STATUS; MAX (max. number of job slots available); NJOBS (# tasks for all jobs dispatched to the host); RUN (# tasks for all running jobs on the host); SSUSP (# tasks for all system suspended jobs on the host); USUSP (# tasks for all user suspended jobs on the host); RSV (# tasks for all pending jobs that have slots reserved on the host)

  • -l displays host information in a (long) multi-line format.

  • -X shows a list of all individual hosts

5.4. bdel <jobID>

The bdel command will remove the specified job via a job-specific stop-file. This will take some time, so if job output is not needed, you can use the bkill command.

5.5. bkill <jobID>

The bkill command will end a job using signal 15 and (if still alive) signal 9 (kill).

If you need to kill all your jobs you can use

bkill -u <UserID> 0

5.6. bmod

Used to modify job settings while job is waiting or running.

  • -b begin_time <jobID> sets a specific start time for a job with id <jobID>
  • -W [hours:]minutes <jobID> resets the runtime limit of a job to the new value

Note: Do have a look at the bmod issue section for proper usage of this LSF command.

5.7. bpeek

  • -f <jobID> attaches to stdout of a running job

5.8. bhist

The bhist command shows history of finished jobs

  • -l <jobID> shows history data of a finished job

5.9. bqueues

The bqueues command shows the available queues

  • -m <host> shows queues for a single host
  • -l <queuename> shows per-user priorities for the different run queues

LSF Job Reporting (New DLP Feature)

The DLP Team has added a new feature, which is giving a detailed information about finished jobs. When using the newly created feature binary, the following additional information will be displayed in the terminal:

  • GPU Utilization Information
  • Total Cost of the Job (GPU Cost (Euro))
  • CPU Information (Number of CPUs, Efficiency)
  • Job Pending Time
  • The Runtime Limit Given By The User
  • Job Summary Containing Grades Whether The GPU, CPU and Memory Were Utilized Properly

6. Compute Job Troubleshooting

6.1. Determine reasons for pending jobs

Determining the reason for a job to stay in the pending state is still a quite difficult task, because there are a lot of reasons possible that can be totally different.
In addition, the schedulers output is not easy to understand if someone does not know how the scheduling algorithm works.
Top pending reasons are

  • Not enough nodes available to satisfy your job resource requirements
  • Not enough licenses available for your job to run
  • Job configured with a dedicated start date in the future
  • Cluster maintenance within requested job runtime
  • New job just submitted and not yet scheduled
  • Array job that has reached the maximum number of concurrently running jobs

The following information will help you to hopefully get to the root cause of your pending jobs.

6.1.1. Detect your pending jobs

A job in a pending state can be identified with the following command:

bjobs -p

The default output will give you basic job details as well as the most prominent waiting reason. Be aware, that reason must not be the root cause for your job to stay pending. A typical output may look like:

JOBID USER STAT QUEUE FROM_HOST EXEC_HOST JOB_NAME SUBMIT_TIME 12345678 mustermann PEND rb_regular si-343l name Jun 11 09:17 New job is waiting for scheduling;

Here, the pending reason stated ("New job is waiting for scheduling;") indicates that this job was just submitted and not yet taken into account by the scheduler.

If "bjobs -p" only returns a single statement, then you most likely have found the root cause for your pending job. Congratulations!

Please see Main LSF pending reasons below for an explanation.

If you see more than a single pending statement, often followed by a statement about host numbers, please continue with the Detailed Step-by-step guide on how to determine reasons for pending jobs.

6.1.3. Detailed step-by-step guide on how to determine reasons for pending jobs

Let's first have a look at how a scheduling algorithm works to fully understand the pending output of the scheduler:

6.1.3.1. A few words on how a job scheduling algorithm works

A scheduling algorithms main task is to map GPU cluster job requests to available resources. Each job needs some cluster resources, that's why you are providing information like number of cores, GPUs and memory needed or the job runtime. A job can only run if enough resources are available on the cluster. Based on a lot of additional parameters (e.g. job distribution requirements, job sizes, node types, priorities, shares, resource limits, etc.) the scheduler has to decide which job is next. It is working together with a so-called "resource manager" that provides it with this information.

The scheduler then loops through the different resources and is performing a matching for each waiting job in the queue starting with the first (and most important) job. When enough resources are available, the matching is successful and this job will run. If not, the scheduler will output all unsuccessful matchings as it does not know by itself which is the most important one.

E.g. if a host is down, the scheduler does not know if the job could have run if this host would have been available. It thus tells you exactly that (e.g. via message like "Load information unavailable: X hosts;" or "Closed by LSF administrator: Y hosts;")

You thus have to identify yourself what is the most reasonable pending reason.

The following pending statements and their explanations are meant to help you on your journey. The scheduler will usually output more than one:

Job's resource requirements not satisfied: X hosts;

This is probably the most important message for you to look further into: it indicates that one or more of your requested resources for your job (slots/cores, memory, runtime, job distribution, etc.) cannot be satisfied by the reported number of hosts. In this case, do the following:

  • Run bjobs -l <jobid> and look for the resource requirements and look for information like
    RUNLIMIT
    MEMLIMIT
    Section starting with [Date]:Submitted from <host>..., e.g.


    Thu Mar 31 12:00:00: Submitted from host <si-343l>, CWD <$HOME/scratch/theano>, Output File <myjobs_testcase_newjob-test.o1234567>, Error File <myjobs_testcase_newjob-test.e123456>, Notify when job ends, Re-runnable, 48 Task(s), Requested Resources < rusage[mem=28672,ngpus_excl_p=2] span[ptile=24] affinity[core]>;
  • Look for any odd numbers. Here, the job is requesting 48 slots, stated as 48 Task(s). 2 GPUs and a resource request of 28GB RAM per core, stated as rusage[mem=28672] using 24 cores per node, stated as span[ptile=24]. This is not fulfillable as the maximum amount of RAM needed per node would exceed 672 GB. We only have nodes up to around 500GB usable RAM available!

Affinity resource requirement cannot be met because there are not enough processor units to satisfy the job affinity request: X hosts;

This is an important one, too! It's a special case of resource shortage: The requested job CPU affinity cannot be provided. The affinity specifies which process task runs on which CPU. We do have dual-socket hosts, so jobs could e.g. fill up a single CPU or could be distributed evenly between both CPUs on a node. For further checks please do the following:

  • Run bjobs -l <jobid> and look for the section labeled RESOURCE REQUIREMENT DETAILS. A typical example might look like

    RESOURCE REQUIREMENT DETAILS: Combined: select[(ngpus>0)&&(ad_access==0&&type == any )] order[r15s:pg] r usage[mem=8192.00] span[hosts=1] affinity[core(1)*1]
  • Look for the "affinity" string in square brackets. Here it's [core(1)*1], which means a single core. This is usually fine, but if you are requesting more than 28 and are also requesting a single host, your job can't run. The same holds true if you are requesting 28 cores on a single host, but all hosts with 28 cores do have at least some cores occupied!
Not enough processors to meet the job's spanning requirement: X hosts;

This is again a special case of resource shortage: The requested job distribution (e.g. cores per node, exclusive/single nodes) cannot be met. For further checks please do the following:

  • Run bjobs -l <jobid> and look for the section labeled RESOURCE REQUIREMENT DETAILS. A typical example might look like

    RESOURCE REQUIREMENT DETAILS: Combined: select[(ngpus>0)&&(ad_access==0&&type == any )] order[r15s:pg] r usage[mem=8192.00] span[hosts=1] affinity[core(1)*1]
  • Have a look at the "span" string in square brackets. Here it's [host=1], which means that your job will be scheduled to a single host. If you had requested more than 28 cores you might be in trouble...
Load information unavailable: X hosts; Shows the number of hosts that are not reporting back to the LSF resource manager. Usually because they are down or LSF is not running on these nodes. You can usually ignore this pending reason.
Not specified in job submission: X hosts; Hosts that you have not specified when submitting your jobs. You are usually not specifying specific nodes when submitting jobs, but your job will always be submitted to a specific queue and not all hosts are available in all queues. You can usually ignore this pending reason if the number of reported hosts is rather small (e.g. <= 3).
Closed by LSF administrator: X hosts; Hosts that have been closed, so they do not accept jobs. You can usually ignore this pending reason.
The available /tmp space (tmp) is low: X hosts; Nodes where /tmp is almost full and no further jobs are allowed to run. You can usually ignore this pending reason.

7. Background Information: Fairshare Scheduling

"Sharing is caring."  "Together we stand, divided we fall."

 Philosophies go longer than just life. Our GPU cluster admires the same and hosts the LSF with similar virtues. 

7.1.1. Why do I need to know about LSF Fairshare scheduling?

You must have had a fair idea till now, on how you could get the resources from LSF and start working. If not, do have a look at the section: Submission of Compute Jobs.

But, you should give a thought on whats happening behind the scenes when you get/request for resources from LSF. And with multiple users, with varied resource requests on the GPU cluster, the question that normally arises when you submit your next job are:

Will my job run immediately ?

I have waited for so long and my job hasn't started yet ? 

How does LSF decide which job to dispatch first ?

Apart from reasons of occupied resources, there is a magic number that stands associated with every user, which LSF uses to prioritize his/her jobs within the cluster. This magic number is called Dynamic Priority and is a key player in LSF Fairshare scheduling.

 

7.1.2. What is LSF Fairshare scheduling?

LSF fairshare scheduling follows a fairshare policy that defines the order in which LSF attempts to place jobs that are in a queue or a host partition within a cluster.
The fairshare policy on the SI cluster is queue based. To have a look at the queues configured to accept jobs from users, type bqueues -u all.

$ bqueues -u all QUEUE_NAME PRIO STATUS MAX JL/U JL/P JL/H NJOBS PEND RUN SUSP rb_interactive 70 Open:Active - - - - 16 0 16 0 rb_basic 60 Open:Active - - - - 18 0 18 0 rb_highend 60 Open:Active - - - - 2843 1072 1090 0

 

For a queue based fairshare, the above mentioned queues have FAIRSHARE mentioned against the field SCHEDULING POLICIES.

$ bqueues -u all -l rb_highend QUEUE: rb_highend -- Queue for GPU jobs running on Volta GPUs This is the default queue. PARAMETERS/STATISTICS PRIO NICE STATUS MAX JL/U JL/P JL/H NJOBS PEND RUN SSUSP USUSP RSV PJOBS 60 0 Open:Active - - - - 2985 1210 1091 0 0 684 418 Interval for a host to accept two jobs is 0 seconds RUNLIMIT 10080.0 min SCHEDULING PARAMETERS r15s r1m r15m ut pg io ls it tmp swp mem loadSched - - - - - - - - - - - loadStop - - - - - - - - - - - SCHEDULING POLICIES: FAIRSHARE BACKFILL EXCLUSIVE RESOURCE_RESERVE


For every queue, there exists a fair share tree. LSF follows this fair share tree which begins at the top with a group and goes down to a single user. 

A user has certain number of shares assigned. Within the same group, users have the same number of shares. Groups, however may have different shares based on the number of GPU units purchased.  Users or Groups that have no shares cannot submit jobs to the queue.

These shares help in calculating the dynamic priority of a user/group. A user's/group's dynamic priority depends on their share assignment and the resources their jobs have already consumed. The order of job submission in the queue is secondary. The important thing is the dynamic priority of the user who/group which submitted the job. With fairshare scheduling, LSF tries to place the job first in the queue that belongs to the user/group with the highest dynamic priority.


7.1.3. How is the dynamic priority calculated by LSF and how can I get to know my dynamic priority?

7.1.4. Fairshare scheduling Takeaways

  • LSF on SI cluster follows fairshare scheduling.
  • The fairshare scheduling is queue based.
  • Every queue follows a fair share tree.
  • Users/Groups have shares assigned, which define a user/group dynamic priority.
  • Without shares, no job can be submitted to a queue.
  • LSF prioritizes job placement in the queue with the highest user dynamic priority by following a top level down approach.
  • The Dynamic priority decreases as more resources are acquired/requested by a user/group.
  • Higher the Dynamic Priority, higher the chances of getting resources faster from LSF.


8. Background Information: Backfill Scheduling

During job execution, no other job from LSF can run on an already allocated job slot/CPU. However, to optimize resource utilization and overall performance on cluster, LSF has a provision named Backfill scheduling. 

8.1.1. What is Backfill scheduling?

Backfill scheduling allows other jobs to use the reserved job slots, as long as the other jobs do not delay the start of another job. Please pay attention to the keyword: "reserved" job slots. 

The job slots on which jobs are already running are occupied job slots , whereas job slots on which a job is scheduled to run are called reserved job slots.

In a busy cluster, you can submit big jobs that are scheduled by LSF to run across multiple job slots. By default, LSF will keep reserving these job slots till the required number of job slots have reached for your job to begin. This would mean a lot of job slots will remain idle until the job starts. This degrades the overall performance of LSF because the reserved resources are idle while other small jobs are waiting in the queue. 

Backfill scheduling helps us in this regard with better utilization of resources. It allows the reserved job slots to be used by small jobs that can run and finish before the large job starts. 

8.1.2. How does Backfill scheduling work?

Assume on a cluster you have a host with 2 Job slots/CPUs. For every job submission, we have a run-time/wall-time limit (using bsub -W ) defined.  The scenario is explained below:

  1. JOB1 with a run limit of 2 hours, using 1 CPU is submitted and gets started at 9:00 am (figure i).
  2. Shortly afterwards, JOB2 is submitted requiring all 2 CPUs. It cannot start right away because JOB1 is already using one CPU, so it reserves the remaining 1 CPU. (figure ii).
  3. At 9:30 am, another job, JOB3 is submitted requiring only 1 CPU and with a run limit of 1 hour. Since JOB2 cannot start until 11:00 am (until JOB1 finishes), its reserved CPU can be backfilled by JOB3(figure iii). Therefore JOB3 can complete before JOB2's start time, making use of the idle CPU.
  4. JOB3 finishes at 10:30 am and JOB1 at 11:00 am, allowing JOB2 to start shortly after 11:00 am ( figure iv).

9. Best Practices on LSF Usage on Cluster

Efficient job submission on the LSF cluster requires following best practices, which can enhance job prioritization and performance. This paragraph will be divided into three stages, which will help you to monitor how well the submitted job is performing.

  1. Preparing job for submission – Key parameters for optimizing CPU, GPU, and memory utilization
  2. During job execution – Key commands for monitoring the status and resource utilization of submitted jobs
  3. After job completion – Utilizing the LSF reporting tool for analysis of completed jobs

9.1.1. Preparing job for submission

The fine tunning of parameters such as number of GPUs, CPUs, Memory Allocation and Runtime will significantly enhance the prioritization rate and the performance of the submitted jobs.  To know how to fine tune those parameters firstly an explanation about the commands and what do they exactly do will be needed. Firstly, the number of the CPU and the related parameters for it, will be explained.

  1. CPU Related Parameters
    1. Parameter “-n”

      To select a certain number of CPUs, which will be allocated for the task, the parameter “-n” must be used.

      For example -n 2 means that 2 CPUs will be allocated for the execution of the task.

      Example "-n" Parameter
      #BSUB -n 2 # min CPU cores,max CPU cores (max cores is optional)

      Disclaimer:

      If the value of the CPU is too high, the job can take time to be executed. Because LSF will search for host with the given number of free CPUs. This can lead to pending state (PEND)

    2. Parameter “span[ptile]”

      Based on how the ptile parameter is selected, it will be decided whether the job will be a single node or multi-node type. This parameter indicated the number of processors on each host that should be allocated to the job.

      Single Node Case:

      This example is for single node execution. Because the number of CPUs is 1 and the ptile is 2. That means 2 cores of the host’s CPU will be used for the submitted job. Maximum cores per node is 28.

      Example Single Node Syntax
      #BSUB -n 1 # Number of CPUS #BSUB -R "span[ptile=2]"


      Multi Node Case:

      To achieve multi node scenario the number of the CPU cores must be greater than 1. In this example the number of cores is 4 and the ptile is equal 1, which means that on each host only one CPU core will be used for the submitted job.

      Example Multi Node Example
      #BSUB -n 4 # Number of CPUS #BSUB -R "span[ptile=1]"
  2. GPU Related Parameters
    1. Parameter “-gpu”

      This parameter is used to define the number of GPUs, which will be needed to fulfill the requirements of the submitted job. When the “-gpu” parameter is used, the job is classified as GPU Job, if this parameter is not defined the job will be classified as CPU Job and there won’t be a GPU Utilization.

      Example:

      In this bsub file the number of GPUs is 1 and mode=exclusive_process means that the GPU will be allocated only for the submitted job

      Example "-gpu"
      #BSUB -gpu "num=1:mode=exclusive_process:mps=no"

      Disclaimer:

      If the number is too high the utilization rate will be lower.
      If the number is too low, the utilization can go over 100 %.

    2. Parameter “mig”

      Mig stands for Multi Instance GPU and this parameter enables a GPU to be divided up to 7 parts, which provides multiple users with independent GPU Resources. Here on the DLP Cluster there are GPUs, which are by default mig and without this parameter the job won’t be submitted correctly.

      Example:

      In this example the job will need 1 GPUs and 1 gpu instance for mig job

      Example "mig"
      #BSUB -gpu "num=1:mig=1"

    This parameter needs fine tuning because each node on the cluster has different memory size because of the running jobs on each node. Also based on the queue, which is used for the job, might vary in memory size.

    To set memory for certain job “-M” is used as parameter and the value of the “-M” is in Mega Bytes. For example -M 2048 means that the memory limit for the submitted job will be 2GB

  4. Runtime Definition
    The correct estimation of the runtime limit also affects the prioritization of the job. To define the runtime, limit the “-W” parameter is used and the value after the parameter is in hours. For example, here 2 hours are set as runtime limit for the job.

    Runtime Definition
    #BSUB -W 2:00 # fill in desired wallclock time [hours,]minutes (hours are optional)

    Disclaimer:

    If the runtime limit is too high the LSF might put your job in pending state since the high runtime means that LSF will need more time to execute this job and jobs with less pending time will be in front of this job and when they are finished, this job will be taken into execution.

9.1.2. During job execution

After the explanation of the parameters and how to fine-tune them for optimal job performance, now this paragraph will provide information on monitoring the status of ongoing task and the utilization of the GPU, CPU, and memory resources.

Commands for the utilization of those 3 resources are provided:

  1. CPU Related Resources (CPU, CPU Efficiency, CPU Average Efficiency)
  2. GPU Related Resources (GPU, allocated GPU)
  3. Memory (Memory Efficiency, Max/Avg Memory Usage, Memory Limit)

Disclaimer:

Bjobs is command, which outputs running jobs and it is not working for already finished jobs. And the parameter “-o” is giving the ability to pick output fields such as jobid, run_time, cpu_used, gpu_num etc. At the end of the parameter there is a mandatory string delimiter=’delimiter is choice of user’, and finally job ID must be provided.

  1. CPU Related Resources

    1. Outputting CPU Usage, Peak Duration and Peak Utilization Efficiency

      CPU Usage
      bjobs -o "jobid run_time cpu_used cpu_peak cpu_peak_reached_duration cpu_peak_efficiency slots delimiter='|'" <job id>

    2. Outputting CPU Average Efficiency

      CPU efficiency
      bjobs -l 6648607 | grep -i "cpu average efficiency"
  2. GPU Related Resources

    These commands must be run in case of GPU jobs. If the submitted job doesn’t utilize any GPU resources, the output of those commands will be empty.

    GPU Example
    bjobs -o "jobid run_time gpu_num gpu_alloc delimiter='|'"

  3. Memory

    Memory is not easy to fine-tune, but there are couple of thinking points before deciding the memory size. The first one is the size of the input, and to fine-tune the memory after couple of test runs.

    1. Outputting average and maximum memory utilization plus memory utilization efficiency.

      Memory Output
      bjobs -o "mem:5 avg_mem:-3 max_mem:3 mem_efficiency memlimit swap slots delimiter='|'"<job id>
